# VFX Code Review — v0.15-qt

**Range:** main..HEAD (f532f91)
**Reviewer:** vfx-code-reviewer
**Date:** 2026-04-19

## Summary

Scope: the bif_qt crate (1817-line `main_window.rs`, ~2.8k lines of hand-written C++), the Renderer winit-decouple (`bif_viewport::Renderer::new` now takes raw `wgpu::Surface/Device/Queue`), and the `bif_qt::viewport` Rust-side bridge (HWND → raw-window-handle → wgpu surface). The architecture is sound: single-thread Qt calls, thread-local `*mut ViewportCallbacks` with documented SAFETY invariants, `wait_for_gpu()` sequenced before Surface/Device drops (the D3D12 OBJECT_DELETED_WHILE_STILL_IN_USE lesson from `d290c9d` has been internalized). Lifetime hazards around the wgpu surface are well handled. The big weaknesses are performance (O(N²) USD traversals in the property inspector), a few latent GPU cleanup edges at shutdown, and ergonomic issues in the ortho / camera-picker paths.

## Blockers

None — nothing in the diff is a production-stopping correctness or safety bug. Ship-with-followups.

## Major

### O(N²) USD stage queries for every property-inspector row
- **File:** `crates/bif_qt/src/main_window.rs:1547,1560,1573,1644,1659`
- **Issue:** `selected_prim_attribute_name_at`, `_type_at`, `_value_at`, `selected_prim_stack_*_at`, and the new `selected_prim_attr_color_index_at` each re-acquire the `UsdStage` mutex and re-run `get_prim_attributes(&path)` / `get_prim_stack(&path)` / `get_attribute_opinions(&path,&name)` per row. A Qt `QAbstractItemModel` calls `data()` ≥3× per visible row per paint (Display/ToolTip/Foreground/ColorIndex roles). For a prim with ~200 attributes that's 800+ full USD attribute traversals per repaint, plus a Mutex lock each time. `selected_prim_attr_color_index_at` is especially expensive: it does `get_prim_attributes` + `get_attribute_opinions` sequentially, each a full stack walk in the C++ bridge.
- **Fix:** Cache per-selection in `BifShellStateRust`. On `selected_prim_pathChanged`, snapshot `Vec<AttrInfo { name, type_name, value, winning_layer_id }>` once; serve the `_at(index)` invokables from that cache. Invalidate on `layer_state_revision` bump. This is the same pattern `scene_layer_state` already uses.

### `is_winning` flag assumed but not verified in attribute opinions
- **File:** `crates/bif_qt/src/main_window.rs:1676`
- **Issue:** The code does `v.into_iter().find(|o| o.is_winning)` but USD value resolution for attributes with time samples and per-frame overrides can pick different winning layers at different time codes. The C++ bridge's `get_attribute_opinions` must be faithfully returning what `UsdAttribute::GetResolveInfo()` says for the default time, or the dot color will mislead artists trying to understand which layer is actually authoring a value at the current frame.
- **Fix:** Verify `cpp/usd_bridge/` sets `is_winning` from `UsdAttribute::GetResolveInfo(time).GetSource()` and uses the shell's `current_frame` rather than `Default`. If not, the color dot is cosmetic-only and is actively misleading for animated stages — document it, or thread `current_frame` through.

### OrthoView ignores viewport aspect ratio
- **File:** `crates/bif_viewport/src/lib.rs:1233-1235`
- **Issue:** `apply_ortho_view` sets `ortho_size = dist * 0.5` — a single scalar. If the viewport is 16:9, the scene will be squashed/stretched unless the projection matrix build path divides by `aspect`. Also: `dist` being user-derived means the initial Top/Front/etc. view frames the scene differently depending on current orbit distance — un-Houdini-like. Artists expect orthographic presets to frame the scene bounds.
- **Fix:** Compute ortho extent from the scene AABB (pad by 10%), and feed `aspect` into the projection so width = `ortho_size * aspect`, height = `ortho_size`. Look at `scene.scene_bounds` (if populated) or recompute from `scene.instances`.

### QTimer fires before Viewport construction — surfaceReady race
- **File:** `crates/bif_qt/cpp/render_widget.cpp:60-71`
- **Issue:** `showEvent` emits `surfaceReady()` and then immediately starts the 16 ms `QTimer` that calls `QWidget::update()` → `paintEvent` → `frameRequested`. Under Qt signal dispatch, if any signal handler defers viewport construction (or if `viewport_on_surface_ready` returns `false` because adapter acquisition fails), the next timer tick invokes `viewport_on_frame` against a `None` viewport every 16 ms. That silent-swallow path is fine today, but it also means transient adapter failures turn into a permanently-black viewport with no user feedback.
- **Fix:** Start `m_tick` only after `viewport_on_surface_ready` returns `true`. Expose a `bool` from the Rust-side signal handler back to the C++ slot. If it fails, surface an error in the status bar instead of spinning the timer against a dead viewport.

## Minor

### `free-fly` reset leaves camera in an arbitrary pose
- **File:** `crates/bif_viewport/src/lib.rs:1243-1249`
- **Issue:** `apply_free_fly` clears locks but does not reset `camera.yaw/pitch/distance/target` — so switching Top → Free leaves the camera stuck looking straight down. Most DCCs restore a sensible orbit pose on free-fly reset (or keep the current transform and un-lock, which is what's implemented). Decide which.
- **Fix:** Either (a) keep current pose silently (current behavior, document it) or (b) re-derive yaw/pitch from `position - target` so orbit controls feel natural. Today, an Alt+drag after Top works but the delta interpretation is weird because yaw/pitch weren't synced.

### `get_timeline()` locked through with_viewport_mut unnecessarily
- **File:** `crates/bif_qt/src/main_window.rs:1382-1387`
- **Issue:** `detect_timeline_from_stage` reaches into `vp.renderer_mut().scene.usd_stage`, clones the Arc, locks it, calls `get_timeline()` — all inside `with_viewport_mut`. This holds the `ViewportCallbacks` thread-local borrow across a USD stage lock. If `get_timeline()` ever does something reentrant (unlikely but possible, e.g. logging into a callback), you have a re-entrancy hazard.
- **Fix:** Use the existing `with_stage` helper (line 74) which already clones the Arc out first specifically to avoid this pattern. `get_timeline` should be callable via `with_stage(|stage| stage.get_timeline().ok()).flatten()`.

### Status message on file-dialog re-entry race
- **File:** `crates/bif_qt/src/viewport.rs:207-210`
- **Issue:** The double-init guard re-uses the existing viewport and routes to `viewport_on_resize`. But `scale_factor` comes from QScreen::devicePixelRatioF() which may have changed if the window was dragged between monitors during the dialog. The guard silently accepts the new DPR, which is correct — but no log line records it, so a regression here would be invisible.
- **Fix:** `log::debug!("viewport re-ready (dialog re-show), resize {w}x{h} @ {scale_factor}x");`

### Camera source key is a stringly-typed enum
- **File:** `crates/bif_qt/src/main_window.rs:1709-1731`
- **Issue:** `active_camera_source: String` encoded as `"free" | "ortho:<Preset>" | "usd:<path>"`. Parsing happens in `on_select_camera` with `strip_prefix`. Any USD camera whose path legitimately starts with `ortho:` or `usd:` (unlikely but not impossible) breaks. More importantly, the match on preset name at line 1716 silently drops unknown presets — if you add "Persp" or "Iso" later and forget to update this match, nothing logs.
- **Fix:** Either (a) add `log::warn!("unknown camera source: {source_str}")` on the else-fallthrough, or (b) introduce a `CameraSource` enum in `bif_qt` and expose it via cxx-qt — more invasive but eliminates stringly-typed parsing.

### Animation stage locks panic on poisoned mutex
- **File:** `crates/bif_viewport/src/animation.rs:400,414,466`
- **Issue:** `stage.lock().expect("UsdStage mutex poisoned")` panics the render thread on poisoning. Poisoning happens when another thread holding the lock panicked. In the Qt path all USD calls are main-thread, so poisoning "shouldn't" happen — but the `.expect` is pessimistic-brittle: one stray panic inside any `with_stage` closure bricks animation forever.
- **Fix:** Match on poisoned and recover: `stage.lock().unwrap_or_else(|e| e.into_inner())` — a stage mutex is effectively read-only from the render thread's perspective, so seeing post-panic state is recoverable.

### `camera_list_revision` not bumped when USD cameras are added via editing
- **File:** `crates/bif_qt/src/main_window.rs:891-900`
- **Issue:** `usd_camera_paths` is snapshotted once at stage-open via `list_camera_prims`. If a future edit op authors a new `UsdGeomCamera`, the picker won't see it until reload. For v0.15.0 this is fine (no edit ops yet), but when v0.16.0 lands, this will be a stale-cache bug.
- **Fix:** TODO comment at line 897 pointing to v0.16 work, or invalidate + re-list on `scene_browser_revision` bump.

## Nits

### `apply_usd_camera` doesn't bump camera_list_revision
- **File:** `crates/bif_qt/src/main_window.rs:1728-1731`
- **Issue:** After applying a USD camera, `active_camera_source` is set but UI listeners relying on `camera_list_revision` don't get told. Right now only the repopulate uses that signal, so it's fine, but if a future "active camera" indicator binds to the revision it will miss updates.
- **Fix:** Either bump `camera_list_revision` inside `on_select_camera` too (for symmetry) or introduce `active_camera_revision`.

### Docstring says "LMB (no mods) → primPickRequested" but accepts on `event->button() == LeftButton`
- **File:** `crates/bif_qt/cpp/render_widget.cpp:96-106`
- **Issue:** Alt+LMB triggers orbit (good); plain LMB triggers primPickRequested in physical pixels. But Shift+LMB and Ctrl+LMB also go to primPickRequested. When selection-with-modifiers lands (multi-select, range-select) this will conflict.
- **Fix:** Only emit primPickRequested when `event->modifiers() == Qt::NoModifier`; forward other modifier combinations as a separate signal now so the Rust side can differentiate later.

### `viewport_on_shutdown` swallows `None` silently
- **File:** `crates/bif_qt/src/viewport.rs:242-248`
- **Issue:** If `cb.viewport` is `None` at shutdown (e.g. surfaceReady never fired), we log "bif_qt viewport shutting down" but never indicate that nothing was torn down. Harmless but misleading in bug reports.
- **Fix:** `log::info!("bif_qt viewport shutting down (viewport_present={})", cb.viewport.is_some());`

## Verdict

**Ship with followups.** The Qt/Renderer boundary is well-designed — single-thread assumption is documented and enforced via thread_local, `wait_for_gpu()` is sequenced correctly before Surface drops, the double-init guard (`d290c9d`) shows the team learned the D3D12 lesson. No unsafe blocks lack SAFETY comments, no Arc/Rc thread-leak hazards, no locks held across FFI callbacks. The two followups that deserve attention before v0.15.0 tags: (1) the property-inspector O(N²) stage queries will bite artists the first time they select a `PointInstancer` with 50 attributes at 60 Hz, and (2) the ortho-preset aspect-ratio bug will be visible on day one in any non-square viewport. Everything else is minor polish or v0.16-era work.
