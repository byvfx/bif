# Code Review: Decompose Renderer (commit 2d65822)

**Reviewer:** VFX Pipeline Specialist
**Verdict:** APPROVE with suggestions

---

## Overall Assessment

Strong refactoring. The decomposition from ~50 fields to ~25 is a meaningful step toward a maintainable DCC architecture. The EventBus pattern is the right call for decoupling UI from logic, and it will survive the egui-to-Qt migration cleanly. The subsystem boundaries are reasonable.

---

## 1. Critical Issues (must fix)

**None.** Clippy passes clean, the refactoring is behavior-preserving, and the event dispatch logic is correct.

---

## 2. Important Improvements (should fix)

### 2a. `SyncViewportToUsdCamera` and `SyncViewportCamera` are duplicate variants

Both variants call the exact same method `self.sync_viewport_to_usd_camera(&camera_path)`. This is a semantic trap -- a future developer will wonder what distinguishes them. Either collapse into one variant or document why two exist.

```rust
// Current (dispatch_events):
AppEvent::SyncViewportToUsdCamera(camera_path) => {
    self.sync_viewport_to_usd_camera(&camera_path);
}
AppEvent::SyncViewportCamera(camera_path) => {
    self.sync_viewport_to_usd_camera(&camera_path);  // identical!
}
```

**Recommendation:** Merge into `SyncToCamera(CameraSource)` using the existing `CameraSource` enum, or at minimum add a doc comment explaining the distinction if there is one planned.

### 2b. `CameraProjectionChange(String)` should be a typed enum

String-matching `"perspective"` and `"ortho:Top"` in dispatch_events is fragile. This is the exact anti-pattern the EventBus was created to eliminate. A typo in any emitter will silently fail.

```rust
// Suggested:
pub enum CameraProjection {
    Perspective,
    Ortho(bif_math::OrthoPreset),
}
// Then: AppEvent::CameraProjectionChange(CameraProjection),
```

### 2c. `ExportEditLayer(String)` -- path should be `PathBuf`

Using `String` for file paths loses platform semantics. Use `std::path::PathBuf` for the export path to stay consistent with `texture_base_dir: Option<PathBuf>` in SceneManager.

### 2d. SceneManager has all `pub` fields -- no encapsulation

Every field on `SceneManager` is `pub`. This means any code in the crate can mutate `instances`, `undo_stack`, `working_scene` independently, breaking invariants. For a DCC undo system this is dangerous -- an edit to `instances.transforms` that skips `undo_stack` is a silent data loss.

**Now:** Acceptable for Phase 1 -- you need to move fields before you can add invariant methods. **Phase 5-7:** Add methods like `apply_transform(&mut self, idx, transform)` that route through undo, and make fields `pub(crate)` or private.

### 2e. `EventBus::drain()` allocates a new Vec every frame

`std::mem::take` returns an owned `Vec<AppEvent>` and replaces with an empty one (no capacity). Next frame, the bus allocates again. For a 60fps render loop this creates ~60 small allocations/second. Not critical now, but easy to fix:

```rust
pub fn drain(&mut self) -> std::vec::Drain<'_, AppEvent> {
    self.pending.drain(..)
}
```

Or keep `std::mem::take` but swap back the drained vec to preserve capacity:

```rust
pub fn drain(&mut self) -> Vec<AppEvent> {
    let mut events = std::mem::take(&mut self.pending);
    // Preserve allocation for next frame
    self.pending = Vec::with_capacity(events.capacity().min(32));
    events
}
```

## 3. Suggestions (consider)

### 3a. `std::mem::take` for EventBus in `run_egui_frame` -- correct but worth a comment

The pattern at line 171 (`let mut event_bus = std::mem::take(&mut self.event_bus)`) is the right way to split the borrow. The existing comment is good. Just noting this is a pattern that should be documented in a "patterns" section if you onboard contributors.

### 3b. `SelectionManager` could own the `select_prim` logic

Right now `dispatch_events` has ~30 lines building `PrimProperties` when handling `PrimSelected`. This logic belongs on `SelectionManager::select_prim(&mut self, path, composite)` -- it would make the dispatch arm a one-liner and make the selection logic testable without a full Renderer.

### 3c. Missing `#[derive(Default)]` -- manual Default impls

Both `SelectionManager` and `SceneManager` implement `Default` manually via `fn default() -> Self { Self::new() }`. Since `new()` is trivial, you could instead `#[derive(Default)]` and remove the manual impl, or keep the manual impl but remove `new()` and just use `::default()`. Having both is redundant but not harmful.

### 3d. Consider `SmallVec` for `NodeGraph(Vec<NodeGraphEvent>)`

Node graph events per frame are typically 0-3. A `SmallVec<[NodeGraphEvent; 4]>` avoids the heap allocation for the common case. Low priority.

### 3e. Test coverage for dispatch_events

The new unit tests for EventBus, SelectionManager, and SceneManager are good and well-structured. However, `dispatch_events` itself has no test coverage. Consider an integration test that creates a Renderer mock/stub, emits events, and verifies state changes. This is hard now (Renderer needs GPU context), but worth planning for when you extract more subsystems.

## 4. Questions / Challenges

### Q1: Why is `scene` pub but `event_bus` is pub(crate)?

`pub scene: SceneManager` is accessible from `bif_viewer::main.rs`, but `pub(crate) event_bus: EventBus` is not. This asymmetry is intentional (main.rs accesses `renderer.scene` directly for gizmo transforms), but it means external code can mutate scene data without going through the event system. Is that the desired boundary?

### Q2: Should `SceneBrowserState` live in `SelectionManager`?

Scene browser state (tree expansion, scroll position, filter text) is UI state, not selection state. If you move to Qt, the tree widget will manage its own expansion state. Consider whether this belongs in a separate `UiBrowserState` that gets discarded during migration.

### Q3: Phase 5-7 ordering?

The commit message mentions phases 5-7 remain (RenderPipelineManager, AsyncWorkManager, methods on subsystems). Given the undo invariant risk in 2d, I'd prioritize adding mutation methods on SceneManager (phase 7 partial) before extracting more structs, so the API hardens before more code depends on it.

## Architecture Verdict

The subsystem boundaries are well-chosen:

| Subsystem | Cohesion | Coupling | Verdict |
|-----------|----------|----------|---------|
| EventBus | High -- single purpose, typed | Zero framework deps | Excellent |
| SelectionManager | High -- all selection state | Imports gizmo, scene_browser, property_inspector types | Good (scene_browser import is debatable) |
| SceneManager | Medium -- "everything scene" is broad | Imports from bif_core, bif_math, gpu_types | Good for now, will need sub-splitting later |

The EventBus is the standout win. Going from 23 string-keyed `egui::Id::new("rebuild_scene_requested")` slots to 17 typed enum variants with compile-time checking is exactly the right move for a production DCC. When Qt arrives, you swap the emit sites and the dispatch logic stays identical.
