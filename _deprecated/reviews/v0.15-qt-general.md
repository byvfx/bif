# General Code Review — v0.15-qt

**Range:** main..HEAD (f532f91)
**Reviewer:** Code Reviewer (general)
**Date:** 2026-04-19

## Summary

The `v0.15-qt` branch brings up a full Qt 6 UI (new `bif_qt` crate, ~8.6k insertions / ~3.1k deletions across Rust + C++) while collapsing `bif_viewer` to a ~20-line shim over `bif_qt::run()` and deleting the old egui chrome. Overall the scaffolding is disciplined: `unsafe` is gated behind documented safety comments citing ADR-007, panic-prone constructs (`.unwrap()`, `panic!`, `todo!`) are essentially absent from the new code paths, and `index as usize` accessors reliably fall back to `unwrap_or_default()` / `unwrap_or(-1)`. Errors propagate through `Result` and surface to the status bar instead of crashing. The main concerns are lifecycle hygiene (double env_logger init, dead `bif_qt_spike` gate crate still in the workspace, code duplication between `bif_qt` and `bif_viewport`), a few stale stubs still wearing "Phase B / v0.14" labels, and the usual "1817-line God module" smell on `main_window.rs`.

## Blockers

None. No correctness or security issues that would prevent merge.

## Major

### Double `env_logger::init()` races between bif_viewer and bif_qt
- **File:** `crates/bif_viewer/src/main.rs:11` + `crates/bif_qt/src/app.rs:16`
- **Issue:** `bif_viewer::main()` calls `env_logger::init()` unconditionally, then `bif_qt::run()` calls `env_logger::Builder::from_env(...).try_init()`. The second call silently fails (via `try_init`), so the carefully-tuned filter `"info,wgpu_core=warn,wgpu_hal=error,naga=warn"` is discarded for users running the shipping binary — they get whatever `RUST_LOG` resolves to through the bare `init()`. That's also why `d290c9d`'s "quiet wgpu_hal" fix only works via `bif_qt_shell`, not the real binary.
- **Fix:** Remove `env_logger::init()` from `bif_viewer/src/main.rs` and let `bif_qt::run()` be the single init site. Optionally drop the unused `env_logger` dep from `bif_viewer/Cargo.toml`.

### `bif_qt_spike` is a declared-dead gate crate still in the workspace
- **File:** `Cargo.toml:10` + `crates/bif_qt_spike/Cargo.toml:10`
- **Issue:** `bif_qt_spike/Cargo.toml` self-identifies as: "GATE crate — delete after Phase 0 decision lands in ADR-006." ADR-006 landed (wiki reference in `bif_qt/Cargo.toml:11`), Phase 0 passed, and `bif_qt` ships the production path. The spike crate still gets built on every `cargo build`, pulls the full `wgpu` + `cxx-build` + `qt-build-utils` stack, and adds ~600 lines of code to maintenance surface. Leaving "delete me" code in the tree is how it becomes permanent fixture code.
- **Fix:** Remove `crates/bif_qt_spike` from `[workspace.members]` and `rm -r crates/bif_qt_spike`. If you want to keep the spike for posterity, git history has it — that's the entire point of git history.

### `denormalize_synthetic_path` duplicated between crates
- **File:** `crates/bif_qt/src/main_window.rs:1762` + `crates/bif_viewport/src/lib.rs` (existing `denormalize_synthetic_path`)
- **Issue:** Same function copied byte-for-byte into `bif_qt` with a comment saying the viewport version is private. Two live copies of path-munging logic is a bug factory — the `/BIF/` prefix scheme or the numeric-suffix rule will evolve and the two sites will drift. Already caught in a commit comment ("Mirrors `bif_viewport::denormalize_synthetic_path` (private to that crate)").
- **Fix:** Promote one copy to `pub` in `bif_viewport` (or `bif_core` — it has no renderer dependency) and delete the `bif_qt` copy. Alternative: make it a method on `Instance::user_facing_prim_path()` so the `/BIF/` contract lives next to the struct that enforces it.

### `main_window.rs` is a 1817-line God module
- **File:** `crates/bif_qt/src/main_window.rs:1-1818`
- **Issue:** The cxx-qt bridge, ~66 invokable implementations, 4 thread-local/static helpers, demo seeding, keyframe lookup, synthetic-path munging, and `BifShellStateRust` struct all share one file. Reviewing it requires paging through five unrelated concerns to find a related invokable. Will be genuinely painful when Phase F adds layer-save mutations.
- **Fix:** Splitting the bridge itself is cxx-qt-hostile (all `#[qinvokable]`s must sit in one `impl` block), but split the non-bridge surface into sibling modules: `invokables/layer_stack.rs`, `invokables/timeline.rs`, `invokables/scene_browser.rs`, `invokables/property_inspector.rs`, `invokables/camera.rs`, each exporting free functions that the thin bridge `impl` block calls through. `BifShellStateRust` and the helpers go to `state.rs`. Leaves the bridge file at ~600 lines of pure plumbing.

## Minor

### Stale version string in About dialog
- **File:** `crates/bif_qt/src/main_window.rs:797`
- **Issue:** `on_about` hardcodes `"bif_qt v0.14.0 (Phase B shell)"` — branch is v0.15 with Phase E.2 + camera picker merged. Users seeing v0.14.0 in Help → About on a v0.15 build will file bug reports for the wrong version.
- **Fix:** Swap the literal for `crate::BIF_QT_VERSION` (already defined at `lib.rs:29` for this exact reason) and drop the "Phase B shell" subtitle.

### Phase B "not yet implemented" stubs still shipping
- **File:** `crates/bif_qt/src/main_window.rs:711` (`on_new_stage`), `crates/bif_qt/src/main_window.rs:720` (`on_open_stage`)
- **Issue:** `on_new_stage` still shows "New Stage — not yet implemented (v0.16)" and `on_open_stage` shows "Open Stage — not yet implemented (Phase C)" — but a user-facing Open path _does_ exist via the sibling `on_stage_path_opened` invokable (wired to QFileDialog in C++). Two invokables with overlapping names, one live and one dead, is a wiring accident waiting to happen if the C++ side ever rebinds to the stub.
- **Fix:** Either wire `on_open_stage` to emit the same `fileOpenRequested` signal the menu action uses, or rename it to `on_open_stage_stub` so the next developer can't confuse them. Same treatment for `on_new_stage` — if v0.16 is months out, make the stub explicitly log + no-op instead of pretending it's a menu option.

### `on_frame_changed` has an unused `&self` bind masked by `let _ = &self`
- **File:** `crates/bif_qt/src/main_window.rs:1305-1309`
- **Issue:** `let _ = &self;` is a comment pretending to be code. It's there to suppress `unused_variables` because the invokable signature is mandated by cxx-qt, but it reads like a mistake during review. A real reader will spend time trying to figure out why `self` is being bound and dropped.
- **Fix:** Rename to `_self: Pin<&mut Self>` at the signature level (supported by cxx-qt 0.7) OR add a one-line doc comment `// self binding required by cxx-qt invokable signature; no state access needed`.

### `load_usd_scene` call is synchronous but claimed "acceptable for now"
- **File:** `crates/bif_qt/src/main_window.rs:838-842`
- **Issue:** Comment acknowledges "blocks on the C++ bridge + GPU buffer uploads" and cites `load_usd_scene_async` as a future fix. On large stages this will freeze the Qt UI thread — `QFileDialog` closes, app hangs for 5-30s, Windows shows "(Not Responding)". Not a blocker, but worth a BUGLIST entry if not already tracked so the async path isn't forgotten once v0.16 lands.
- **Fix:** File a tracking issue referencing the `scene_manager::load_usd_scene_async` migration path, or add a `#[doc(hidden)] // TODO(v0.16): switch to async load` above `on_stage_path_opened` so it shows up in grep sweeps.

### Viewport re-creation guard recursively calls `viewport_on_resize` with a known-raw HWND path
- **File:** `crates/bif_qt/src/viewport.rs:206-210`
- **Issue:** When `surfaceReady` fires twice (hide+show around file dialog), the guard calls `viewport_on_resize(cb, width, height, scale_factor)` and returns `true`. Fine — but the `width/height` passed in are the _new_ show's dimensions, which might not match the prior surface's swapchain. If the HWND itself changed between hide/show (Windows can recreate native handles on reparent), silently resizing without rebuilding the surface will render to a stale HWND. Unlikely for the file-dialog path, but `d290c9d` already had to fix one double-init crash here.
- **Fix:** Add a debug assertion or log line comparing the current `hwnd` to the one captured at `Viewport::new` time. If they differ, tear down and re-create rather than resize.

### C++ `TODO(tier2)` in `window_builder.cpp` risks losing the layer-palette source-of-truth
- **File:** `crates/bif_qt/cpp/window_builder.cpp:224`
- **Issue:** Comment reads "LAYER_PALETTE. TODO(tier2): consolidate into a shared header." There's already a `LAYER_COLORS` palette in `bif_qt/src/theme.rs:88-98` + a cxx-qt pathway. Any time the Rust palette changes, the C++ copy will go stale and the UI will show different colors in different panels.
- **Fix:** Expose an `#[qinvokable] fn layer_palette_qcolor_at(index: i32) -> QColor` so C++ sources colors from Rust. Until then, leave a `static_assert` or comment cross-ref with the Rust line number so drift fails loud.

## Nits

### `anyhow` dep declared but only used via `Result<i32>` at one call site
- **File:** `crates/bif_qt/Cargo.toml:36` + `crates/bif_qt/src/app.rs:9`
- **Issue:** `bif_qt::run()` uses `anyhow::Result<i32>` but never attaches context or chains — `Ok(rc)` is the only construction. Could be `Result<i32, std::io::Error>` or a bare `i32` return with a panic on failure paths (there are none that return Err today).
- **Fix:** Either add `.context(...)` calls in viewport init so the anyhow dep pays for itself, or downgrade to a plain return type. Not urgent.

### `seed_demo_layer_stack` will ship in release builds
- **File:** `crates/bif_qt/src/main_window.rs:1061-1115`
- **Issue:** "Phase C.1 visual testing" demo data seeding sits in the release code path with no `#[cfg(debug_assertions)]` gate. Only consequence is a few KB of string literals in the binary and an invokable that does nothing useful for users.
- **Fix:** Gate behind `#[cfg(debug_assertions)]` or move to a `#[cfg(test)]` module. If the command palette still surfaces it, hide the palette entry behind the same gate.

### `Viewport::new`'s `scale_factor.max(0.1)` silently accepts sub-unity DPR
- **File:** `crates/bif_qt/src/viewport.rs:112` + `:134`
- **Issue:** Clamping to 0.1 means a misconfigured screen reporting DPR 0 gets a 10x scale mismatch instead of a loud error. Qt's `devicePixelRatioF()` returns 1.0 for normal screens, 2.0+ for HiDPI; 0.1 is unreachable in practice but also meaningless as a floor.
- **Fix:** Use `.max(1.0)` as the floor — HiDPI never goes below 1.0 in any supported platform — and log a warning if the input was < 0.5.

### `denormalize_synthetic_path` silently accepts empty paths
- **File:** `crates/bif_qt/src/main_window.rs:1762-1773`
- **Issue:** Given `/BIF/` (trailing slash stripped leaves empty), the function returns `""`. Downstream `selected_prim_path` setter then shows an empty pill. Not a crash, just confusing UX if the picker ever misbehaves.
- **Fix:** Return `Option<String>` so callers can skip empty results, or debug-assert the invariant.

## Verdict

**Ship with follow-ups.** Nothing blocks merge. The Qt migration landed cleanly — `unsafe` is documented, panics are absent, errors propagate. The follow-up list is dominated by housekeeping (dead spike crate, doubled env_logger init, duplicated helper, stale About string) and one architectural nudge (split `main_window.rs`). None of them compound into a correctness hazard in the next phase; all of them will cost ~2× as much to address once v0.16 piles mutation paths on top. File the spike-crate removal and the env_logger fix as immediate post-merge cleanup, track `main_window.rs` split as a Phase E.3 prerequisite, and ship.
