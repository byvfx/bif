## What I Did

### Static trace settled half the bug before touching the app

Traced the whole HDRI param flow rather than guessing from the symptom:

- **Live update: confirmed broken, statically.** Spinboxes (`node_graph_widget.cpp:106-114`) have **no `valueChanged` connects**, and there was **no bridge fn at all** for a param-only update. The egui build emitted `NodeGraphEvent::UpdateHdriParams` (`property_inspector.rs:1818`); the Qt port never got a counterpart. The backend handler (`node_dispatch.rs:118-133`) was there and correct the whole time — only the UI half was missing.
- **Apply: the chain is correct end to end.** `on_hdri_apply` → `on_node_graph_load_hdri` → `node_graph_load_hdri` → `snarl_load_hdri` writes the node → `LoadHdri` → `start_hdri_load` bakes `rotation.to_radians()`+intensity → `poll_ibl_result` → `apply_ibl_result` sets GPU params **and** `ivar_state.hdri_rotation/intensity` (`render.rs:373-375`). Shaders consume both (`skybox.wgsl:74-75`, `basic.wgsl:368-380`); the CPU tracer uses `config.hdri_rotation.unwrap_or(env.rotation())` (`renderer.rs:162-163`). `get_node_info` emits both keys.

So Apply can't be a wiring gap. Either it was never actually broken, or it was hitting a silent early return: `with_viewport_mut(...).unwrap_or(false)` swallows renderer-not-ready, and `snarl_load_hdri` returns `None` on id/type mismatch. **Neither logs.**

**Smoke test settled it: Apply was never broken.** After the live-update fix, scrubbing *and* Apply both work. So there was only ever **one** bug — the missing `valueChanged` wiring. The 2026-07-31 "Apply also fails" note was a misread: with no live update, the panel gave no feedback at all, and the silent `unwrap_or(false)` bridge meant a working Apply and a dead one looked identical. I kept the bridge-feedback change anyway — it's what would have made this a one-session diagnosis instead of two, but it's **hardening, not a fix for an observed failure**, and the CHANGELOG says so.

### Key decisions

- **Degrees stay the panel/node/event unit; radians start at `UpdateHdriParams`.** `update_environment_params` takes radians and assigns straight into `gpu_env.params` + `ivar_state`, so calling it directly from the new method would have been a silent 57× error. Dispatching the event keeps one conversion site.
- **Params-only update does NOT set `scene_graph_dirty`.** Env params change lighting, not topology — dirtying it would force a full working-scene rebuild on every spinbox step. Asserted in a test so it can't regress.
- **`QSignalBlocker` on panel repopulate.** `show_params_for` calls `setValue`, which would otherwise emit `valueChanged` and echo the node's own values back at the backend on every node select.
- **Success is quiet on the live path, loud on Apply.** Live fires per spinbox step; a status message per step would be churn.

## Learnings

- **Trace the whole path before filing.** The symptom said "intensity/rotation don't work" and the 07-31 note called it two bugs. The trace found one missing path (no wiring) and one path that was demonstrably correct — and the smoke test confirmed the second was never broken. Filing on the symptom would have produced a phantom issue.
- **A user-reported symptom can be one bug wearing two hats.** "Live update does nothing" and "Apply does nothing" read as two failures; with no live wiring *and* a silent bridge, one defect produced both appearances. Worth distrusting a symptom count until the path is traced.
- **A silent `unwrap_or(false)` at a UI bridge costs more than the bug it hides.** Three setters had it. It turned a one-run diagnosis into a parked issue.
- **On a network working tree, trust `git status` over `Test-Path`.** The filesystem layer lies about existence; git had already noticed the files were gone.
