### Killed the debugger dependency before installing one

Session opened blocked on installing Debugging Tools for Windows. Checked the
Application event log first — **Windows had already recorded all three crashes**
with faulting module and fault offset. Both `bif_viewer.pdb` and
`Qt6Widgets.pdb` were on disk, and `dbghelp.dll` ships with Windows, so a
~60-line P/Invoke script turned those offsets into file:line. No SDK, no `cdb`,
no admin.

Symbolized results, and they reframed the whole issue:

| When | Location |
|---|---|
| 08/19 | `bif_qt/cpp/node_graph_widget.cpp:385` (`scene_pin_pos`) |
| 08/10 | Qt `qgraphicsitem.cpp:7465` |
| 08/09 | Qt `qgraphicsitem.cpp:5837` |

All three in the node graph **UI**, none in the renderer. That explains why last
session's render-loop instrumentation kept showing clean frames and 31 complete
frames after the last event — the fault was never in `render()`. Two sessions of
tracing had been aimed at the wrong subsystem.

### Root cause: wire lifetime

`BifNodeWire` holds raw `BifNodeGraphicsItem*` for both endpoints.
`delete_selected_nodes()` deleted the node and never touched `m_wires`, so a
wire kept a dangling endpoint, stayed in the scene, and faulted on the surviving
node's next `moved()` → `refresh()` → `scene_pin_pos()` → `scenePos()`.

The `if (!m_from_node || !m_to_node)` guard is useless here — **a pointer to a
deleted object is not null**. The comment at the connect site stated the false
assumption outright: *"when from/to is destroyed the scene is tearing down so
wire will be gone shortly after."* True at shutdown, false for a single delete.

Second leak, same shape: the reconnect path deleted a wire but left both
`moved()` lambdas connected, holding a dangling `wire` capture.

Fixed at the choke point instead of per call site — the wire adopts its two
`QMetaObject::Connection`s and disconnects them in a destructor, and
`remove_wire()` / `remove_wires_for_node()` centralize teardown.

### Proved it rather than assuming it

Having been wrong on #28 twice, built a pre-fix binary alongside the fixed one
and ran a controlled A/B. Also added logging to `connect_pins`, which was
completely silent — meaning no log could answer "did a wire exist?", which is
the only question that matters for this bug.

The first test run was **void**: no wire was ever connected and both nodes were
deleted, so `m_wires` was empty — safe even pre-fix. The added logging caught
that. Re-ran properly:

| | pre-fix | fixed |
|---|---|---|
| `connected node:0:0 -> node:1:0` | yes | yes |
| `deleted node:0` | yes | yes |
| after dragging survivor | log ends, hard death | `shell exited rc=0` |

Identical armed sequence, single variable.

## Learnings

- **Check the OS crash log before reaching for a debugger.** WER records
  faulting module + offset for every unhandled exception. With the PDB on disk
  that is often the whole answer, and `dbghelp.dll` is already installed.
- **Symbolizing against a rebuilt binary yields a confident wrong answer.** The
  first automated run resolved a stale crash against a since-rebuilt exe and
  printed a plausible line number that was pure garbage. The script now compares
  the PE `TimeDateStamp` against the one WER recorded and refuses to symbolize
  on mismatch.
- **A null check does not make a raw pointer safe.** Endpoint pointers need
  lifetime coupling, not validation.
- **Silence in a bridge fn is a debugging tax.** `connect_pins` logging nothing
  is why the first verification run was void without anyone noticing. Same
  lesson as the #29 three-way feedback work.
- **Instrumentation confirms where you point it.** The `trace28` markers were
  correct and useless — they proved the render loop was healthy, which was never
  in question once WER was consulted.
