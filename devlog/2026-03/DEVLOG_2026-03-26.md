## What I Did

### Per-Tile UDIM Loading (6 phases)

1. **Shared tile infrastructure** — Added `UdimTileInfo`, `UdimGridLayout`, `UdimTileSet` to bif_core with per-tile sampling (resolve tile from UV floor, sample with fract UV)
2. **CPU renderer integration** — `OpenPbrSurface` checks UDIM tile set before single texture for all 5 material slots
3. **GPU viewport loading** — `prepare_texture_placeholders` and `start_texture_loading_async` expand UDIM patterns into individual tile paths, allocate contiguous texture array blocks
4. **GPU types** — `UdimGpuMapping` struct, `MaterialGpu::from_material` uses `udim_map` for base index + grid metadata
5. **Shader** — Replaced atlas UV remapping with per-tile lookup: `textures[base_idx + row * cols + col]` with fract UV. Eliminated row-flip logic.
6. **Cleanup** — Removed atlas stitching, UDIM disk cache, scale_pixels_box, ClearUdimCache UI, serde_json dep, old atlas tests

### Key architecture decisions

- UDIM pattern maps to base_index in texture array; tiles occupy contiguous block at `base + row * cols + col`
- Missing tiles in sparse UDIMs get default white texture (placeholder stays)
- `UdimTileSet` in bif_core is UI-agnostic — individual tiles accessible via `get_tile(col, row)` for future material editor

## Learnings

- wgpu's `binding_array` with dynamic indexing makes per-tile UDIM trivial on GPU side
- The row-flip logic in the old atlas stitcher was a source of bugs — per-tile eliminates it entirely
- Sparse UDIM grids waste texture array slots (e.g. 3 tiles in a 5x3 grid = 15 slots). Future: indirection table or denser packing
- VFX code review caught the `tex_offset` omission early — would have been a silent bug when roughness/normal sampling is added to the shader

### Fix: Zombie Process + Unsaved Changes Dialog (~1 hour)

**Problem:** Two close-related bugs: (1) process lingers in Task Manager after window closes, (2) "unsaved changes" save dialog never appears on quit.

**Root causes found:**

- **Zombie:** After `event_loop.exit()`, Renderer drops wgpu Device, USD C++ stage, Embree scenes. Native DLL finalization deadlocks on Windows loader lock. No `process::exit()` as safety net.
- **Save dialog:** `project.dirty` only set in 2 places (property inspector, node graph mutation). Gizmo drags, undo/redo, keyframes never marked dirty.
- **Dialog z-order:** rfd `MessageDialog` on Windows appears behind main window even with `set_parent()`. Native Win32 modal dialog z-order issue.

**Fixes:**

1. Added `self.project.mark_dirty()` to `push_transform_command`, `undo`, `redo`, `set_keyframe`
2. Added `std::process::exit(0)` after `event_loop.run_app()` in main.rs
3. Stored `Arc<Window>` in Renderer, hide main window before showing rfd dialog, restore after
4. Confirmed zombie bug live — process PID found locking exe during build

### Fix: OIDN using geometric normals instead of shading normals (~15 min)

**Problem:** OIDN denoiser was receiving geometric (face) normals instead of shading normals (post-normal-map, interpolated). Denoising edges followed faceted geometry rather than shading detail.

**Root cause:** Both normal types already computed in `renderer.rs` (`aov.normal` = geometric, `aov.shading_normal` = shading), but both OIDN call sites passed geometric.

**Fix:** Swapped to shading normals in both paths:

- `batch_render.rs:508` — `result.normal` → `result.shading_normal`
- `ivar_build.rs:1025` — `normal_buffer` → `shading_normal_buffer`
- Updated `denoise.rs` doc comment to clarify expected normal type
