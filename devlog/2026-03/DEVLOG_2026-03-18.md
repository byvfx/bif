# Development Log - 2026-03-18

## Session Duration
~30 minutes

## Goals
- Fix UDIM vertical tile-swap bug in Ivar CPU sampling

## What I Did
- Diagnosed double V-flip: `transform_uv()` returned pixel-space (0=top) UVs, then `sample()` applied `1.0 - v` again — net effect swapped tile rows in multi-row UDIM grids
- Removed `flipped_row` and `(1.0 - sub_v)` inversion from `transform_uv()`, now returns UV-space `(row + sub_v) / grid_rows`
- Updated doc comment to accurately describe V-axis convention
- Updated `test_transform_uv_2x2_grid` assertions (row=0 tiles: 0.75→0.25, row=1 tiles: 0.25→0.75)
- Verified `test_udim_sample_tile_color` unaffected (1-row grid, both formulas give 0.5)
- Fixed pre-existing rustfmt issue in `bif_viewport/src/render.rs`
- VFX code review: added `test_udim_sample_2x2_grid` (end-to-end 2x2 sample test with 4 tile colors)
- Added inline comment in `build_udim_atlas` explaining flipped_row convention relationship
- Fixed `transform_uv` doc comment wgsl line ref (281-305 → 287-310)

## Key Decisions
- GPU shader (`basic.wgsl`) was already correct — it uses `textureSample()` directly with no second flip
- Fix is CPU-only: `transform_uv()` + `sample()` path used by Ivar renderer

## Learnings
- UV convention mismatch between GPU (texture sampler handles flip) and CPU (manual `1.0 - v`) is a common source of UDIM bugs
- 1-row UDIM grids mask this bug since `row / 1 = 0` and `(grid_rows - 1 - row) / 1 = 0` are identical

## Session b — .tx Loading + OIIO Mip Fix

### Duration
~1.5 hours

### Goals
- Enable .tx texture loading by default when OIIO feature active

### What I Did
- Flipped `prefer_tx: false` → `true` in `TextureCache::new()` and `with_base_dir()`
- Added `info`-level log when loading .tx, `debug` when falling back to source
- Discovered crash (STATUS_ACCESS_VIOLATION) when loading .tx files with embedded mipmaps
- Root cause: `oiio_load_texture_with_mips()` in `oiio_bridge.cpp` passed `miplevel=0` to `read_image()` in the mip loop instead of actual mip index — read full-res (1024x1024) into buffers sized for smaller mips (512x512, etc.)
- Latent bug since M22 — never triggered because PNGs have 1 mip level
- Fix: `read_image(0, 0, ...)` → `read_image(0, mip, ...)` in all 3 mip read call sites
- Attempted auto-convert at load time, reverted — too slow (28s/texture) + Windows file locking race

### Learnings
- OIIO `read_image(subimage, miplevel, ...)` — miplevel is explicit, not inherited from `seek_subimage()`
- Debug `fprintf` in C++ bridge effective for isolating FFI crashes
- Windows prevents rename-over-open-file — OIIO maketx temp→rename fails if .tx is still open
