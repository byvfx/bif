## Goals

- Debug why Pixar's PointInstancedMedCity.usd renders no instances in BIF

## What I Did

### Investigation

- Inspected PointInstancedMedCity.usd via Python/pxr: 40K instances, 8 Xform prototypes each wrapping a Mesh child
- Discovered all instancer attrs (positions, orientations, scales, protoIndices) authored ONLY at time sample t=184.0 with no default values
- `ComputeInstanceTransformsAtTime(Default)` returns 0 transforms; `ComputeInstanceTransformsAtTime(0)` returns 40K

### Bug 1: Time-sampled data read at Default time (C++ bridge)

- `cpp/usd_bridge/usd_bridge.cpp` — instancer caching used `UsdTimeCode::Default()` for all reads
- Fix: added `evalTime` fallback that checks time samples on positions/orientations/scales, uses stage `startTimeCode` or first sample
- Applied to: GetProtoIndicesAttr, ComputeInstanceTransformsAtTime, velocities, angular velocities

### Bug 2: Xform vs Mesh prototype path mismatch (Rust loader)

- Instancer targets: `/Prototypes/prototype_0` (Xform), but prototype_map keys: `/Prototypes/prototype_0/mesh_0` (Mesh)
- Fix: after inserting mesh path into prototype_map, also insert parent Xform path via `entry().or_insert()`
- File: `crates/bif_core/src/usd/loader.rs`

### Test asset

- Added `assets/PointInstancedMedCity.usd` from Pixar for testing

## Learnings

- USD PointInstancer data can be entirely time-sampled with no default values — must handle this case
- Common USD pattern: PointInstancer prototype targets are Xforms wrapping child Meshes, not Meshes directly
- `ComputeInstanceTransformsAtTime` interpolates/holds values for any numeric time code, even outside the authored sample range

### What I Did

- Scoped two realistic features for BIF: many-light sampling (light tree) and env map visibility cache
- Implemented Phase 1 immediately: power-weighted light selection in `LightList`
- Added `luminance()` helper, `power()` to `Light` trait with impls for all 3 light types
- Replaced uniform 1/N sampling with CDF-based power-weighted selection
- Updated `pdf()` and `pdf_for_light()` to use power weights
- Added zero-power uniform fallback
- 9 new tests (power values, CDF, distribution, edge cases)

### Learnings

- Octane's "AI Light 2.0" is actually just hierarchical light sampling (Estevez & Kulla 2018), not neural
- Power-weighted sampling is unbiased — same pixel values, just lower variance per sample
- `partition_point` is Rust's binary search for CDF lookup — clean and correct
- Per-light `samples` USD attribute is renderer-specific, not a standard; power-weighting replaces most of the need
