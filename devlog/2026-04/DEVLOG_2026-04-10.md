## Key Decisions

- **Embed skin data on `Mesh`** (not separate `SkinnedMesh` wrapper). Locked in during planning; paid off — loader plumbing + renderer hookup are trivial.
- **Viewport-only playback for v0.13.5**. Ivar renders current frame as snapshot on render request (no per-frame BVH rebuild). Stays within 20-30h budget.
- **Defer blend shapes to v0.13.6**. Separate FFI + delta math + per-time weight eval, worth its own focused scope.
- **Correct normals via inv-transpose 3×3** (not fast-path same-as-position). User preference; pays ~1 Mat3 inversion per joint per frame.
- **Hand-authored fixture + real character**. Fixture deterministic for unit tests, HumanFemale catches real-world issues (anim range, joint count mismatch between anim source and skeleton, etc.).

## Problems + Solutions

- **HumanFemale anim test delta=0**. Initially queried time codes 0 and 20, which are outside the fixture's 101-129 authored range; USD clamps out-of-range queries to the nearest keyframe, so both returned the frame-101 pose. Fixed by using `stage.get_timeline()` start/midpoint. Passed with max delta 39.5.
- **SSO UAF in `joint_path_ptrs`**. Original code captured `.c_str()` before `std::move` into the vector; short joint names ("Root", "Bend") fit in SSO and would dangle after the move. Fixed by populating pointers in a second pass after all pushes complete.
- **Mesh ownership from renderer**. Needed access to `bind_positions` and `SkinBinding` per frame without violating `Arc<Mesh>` immutability. Solution: snapshot both into `SkinnedMeshEntry` at registration time (copy cost amortized — once at load, never again).
- **Stale incremental artifacts after adding `skinning` module**. LNK2019 unresolved externals in `bif_core` test binary referencing dropped `Texture`/`CubemapFace` destructors. `cargo clean -p bif_core` + rebuild fixed it. (Pre-existing bif_perf link errors unrelated to my changes, noted for future cleanup.)
- **Pre-existing 9 export test failures on clean main** (unchanged by my work — verified via stash/unstash). Noted in session handoff.

## Learnings

- **UsdSkelCache is the canonical API** for skinned scene data. Raw `UsdSkelSkeleton::GetBindTransformsAttr().Get()` misses composition + layer overrides and can't do time-varying eval. Always go through the cache.
- **USD time code clamping is silent**. Querying outside `startTimeCode..endTimeCode` returns the nearest keyframe without warning. Test assertions over animation deltas must use the authored range.
- **Glam's disjoint-field borrows work**. `skin_positions(&entry.skin, &entry.bind_positions, &palette, &mut entry.skinned_scratch)` compiles — Rust's borrow checker allows immutable + mutable borrows through distinct fields of the same struct in the same expression.
- **The viewport's `vertex_animated_meshes` pattern scales perfectly to skinning**. Adding `skinned_meshes` as a parallel list with its own update function fit the existing architecture without surgery.
- **`bif_perf` has stale incremental-artifact link issues** — anything touching a widely-used type (like `Mesh`) triggers LNK1120. Needs a proper investigation + possibly clean config.

## Phase 5: HumanFemale Validation Debugging

Visual validation against Pixar's HumanFemale.walk.usd surfaced six layered bugs that the synthetic fixture didn't catch. Each had a distinct symptom and a distinct fix:

### Bug 1: Multi-draw mode silently skipped

- **Symptom:** character loaded but didn't deform at all (only the prim-level transform animation moved).
- **Cause:** Phase 3's `update_skinning` had a one-time warning + early return for `multi_draw.enabled == true` — deferred per the v0.13.5 plan.
- **Fix:** added `MultiDrawState::update_skinning` (mirrors `update_vertex_animation`'s structure) that walks `prototype_gpu_data`, computes per-entry palette via the supplied closure, runs LBS into the entry's scratch, writes each prototype's `vertex_buffer`. `animation.rs::update_skinning` now delegates to it instead of returning early.

### Bug 2: Per-mesh joint indices in mesh-local order, not skel-global

- **Symptom:** mesh exploded into scattered triangle islands.
- **Cause:** UsdSkel meshes can author a custom `skel:joints` primvar that's a SUBSET (or reordering) of the skeleton's joint order — common optimization (a hand mesh only carries hand joints). `ComputeJointInfluences` returns indices into THIS local order, not the skeleton's. My code assumed they were skeleton-global.
- **Fix:** in `cache_skeleton_data`, build a `mesh_joint_path → skel_joint_idx` lookup via `UsdSkelBindingAPI::GetJointsAttr` matched against `UsdSkelSkeletonQuery::GetJointOrder`. Remap each influence index through the map; -1 sentinel for unmappable. Rust loader converts -1 → `u32::MAX` so the bounds check drops it cleanly (vs the previous `i.max(0) as u32` which silently mapped -1 to joint 0).

### Bug 3: UV-seam vertex expansion mismatch

- **Symptom:** after Bug 2 fixed, character coherent but with vertices collapsing to origin at every UV seam — visible as huge triangles spanning origin to body parts.
- **Cause:** the C++ bridge already duplicates vertices across UV seams for `faceVarying` UV support (e.g. `orig=32890, mesh=35268` for the body). `mesh.positions` has the post-split count. But `ComputeJointInfluences` returns influences for the ORIGINAL pre-split count. Every post-split duplicate vertex past the original count had no joint data → bounds-checked out of `joint_indices` → `accum = Vec3::ZERO` → collapse to origin.
- **Fix:** the bridge already tracked `vertex_index_map[split_idx → orig_idx]` for vertex animation. Reused it in `cache_skeleton_data`: walk each post-split vertex, copy the influence block from `orig_idx * element_size`. Output now has `post_split_vert_count * element_size` entries, perfectly aligned with `mesh.positions`.

### Bug 4: Rigidly-deformed accessories disappearing

- **Symptom:** body coherent and walking, but hair, buttons, eyelashes, and teeth missing or floating in wrong locations.
- **Cause:** accessories without per-vertex `jointIndices` are bound rigidly to a single joint with constant interpolation. `ComputeJointInfluences` returns ONE influence block (not per-vertex), and `IsRigidlyDeformed()` is true. My code's per-vertex iteration bounds-checked out for every vertex past 0 → entire mesh dropped to origin.
- **Fix:** detect `IsRigidlyDeformed()` and broadcast the single block to every post-split vertex BEFORE the UV-split expansion path. After this branch, the layout invariant `joint_indices.len() == post_split_vert_count * element_size` holds for both rigid and per-vertex meshes.

### Bug 5: SkelRoot world xform vs sub-Xform offset double-application

- **Symptom:** rigid accessories visible but in the wrong locations (hair attached but slightly off, buttons floating in front of the chest at 2x offset).
- **Cause:** the skinning math produces vertices in **skel-local space** (`ComputeJointSkelTransforms` is skel-local). BIF then applied each mesh prim's own **world transform** as the instance matrix. For meshes at the SkelRoot origin (the body, hair attached at head), the mesh's world ≈ SkelRoot's world, so the result was correct. For meshes under sub-Xforms (like `/HumanFemale_Group/KidThinButtonDown/Geom/Render/Buttons/Button1/Button1_sbdv/Button1_Button_sbdv` translated to the chest), the mesh's world transform = `world_skelroot * local_button_offset` where `local_button_offset` was ALSO baked into `geomBindTransform` — double-application of the chest offset.
- **Fix:** plumbed `skel_root_world_xform[16]` through `CachedSkinBinding` → `UsdBridgeSkinBindingData` → `UsdBridgeSkinBindingDataRaw` → `UsdSkinBindingData`. C++ bridge populates it once per SkelRoot via `UsdGeomXformCache::GetLocalToWorldTransform(skel_root_prim)`. Loader uses it as the static instance transform for any mesh with a valid skin binding — `instance_xform = SkelRoot world * skel_local_skinned_vertex` correctly anchors at the SkelRoot regardless of where the mesh prim sits in the hierarchy.

### Bug 6: Per-frame xform animation overwriting the static override

- **Symptom:** after Bug 5 fixed, buttons STILL in wrong location, looked identical to before.
- **Cause:** every HumanFemale mesh prim has its own keyframe animation (89/89 instances). BIF's `AnimatedTransform::with_keyframes` evaluates these per-frame and overwrites the static instance matrix every frame. So my SkelRoot world override only held for one frame at load — animation immediately replaced it with the button's own per-frame world xform, re-introducing the double-application.
- **Fix:** track `is_skinned` in the loader and SKIP the `AnimatedTransform::with_keyframes` branch entirely for skinned meshes. They get a static instance transform (= SkelRoot world); all per-frame motion comes from the joint deformation pass. Confirmed fix: HumanFemale renders fully coherent, walks correctly, all 77 prototypes deform.

### Tooling lessons

- **`usdtree` showed only the top prim** because the file uses payloads — geometry is loaded lazily. `Usd.Stage.Open(...).Traverse()` from Python expands payloads and gives the full hierarchy.
- **`UsdGeom.XformCache().GetLocalToWorldTransform(prim)`** plus printing `GeomBindTransformAttr().Get()` and `GetJointIndicesPrimvar().GetInterpolation()` was the diagnostic that nailed Bugs 2-5. Going through the actual file rather than guessing was 10x faster than speculating.
- **Targeted log diagnostics paid off** — adding "first call entry count + multi_draw state" to `update_skinning` immediately revealed Bug 1. Without that, I would have stared at the math for an hour.

## Phase 6: Code Review Follow-up

After v0.13.5 shipped (commits c937e0f → 993067b), ran two parallel code reviews via specialized agents (`vfx-code-reviewer` and `Code Reviewer`). They surfaced ~15 concerns. Verified each one against the actual code instead of acting on assumptions:

**Refuted by code reading (false alarms):**

- `is_skinned` "not wired" — actually wired at `loader.rs:258` via `if !is_skinned && scene.timeline.is_some()`.
- Palette order math "wrong" — associatively equivalent to USD's convention; HumanFemale's buttons (which DO have non-identity geomBindTransform per python inspection) render correctly, which is the strongest possible validation.
- Normals test "vacuous" — actually uses `Mat4::from_scale(Vec3::new(2.0, 1.0, 1.0))`, real non-uniform scale exercise.
- `joint_path_ptrs` SSO fixup "fragile" — no future pushes to `bridge->skeletons` after the fixup loop, safe today.
- Borrow scope "unnecessary" — actually required by NLL (mutates `mesh_data.vertices` while iterating `skinned_meshes`).
- Scratch resize "dead code" — defensive guard for future dynamic resizing; harmless cost.

**Real issues, fixed in this commit:**

1. **77 redundant `compute_skel_xforms` calls per frame.** HumanFemale's 77 prototypes all bind to one skeleton, but the per-entry closure called the FFI 77× per frame for the same data. Fix: built a `HashMap<usize, Vec<Mat4>>` cache per call in both `animation.rs::update_skinning` paths (multi-draw delegation + inline single-mesh). Closure on `MultiDrawState::update_skinning` changed from `Fn` to `FnMut` to allow the captured cache. Collapses N FFI calls per frame to (number of unique skeletons), which is 1 for any single-character scene.
2. **Double `.unwrap()` in loader log** at `loader.rs:277-281`. Hoisted local bindings before the `mesh.skin = Some(...)` move so the log uses owned values directly.
3. **Lock-down test for non-identity geomBindTransform.** Added `non_identity_geom_bind_round_trip` to `skinning.rs` with three sub-cases (identity joint, translated joint, rotated joint). All three pass on the first run, locking the math against future regression. Total skinning unit tests: 9.

**Documented as known limitations** (in `wiki/usd/usdskel-import.md`) for future versions:

- Animated SkelRoot xform (character on moving platform) not handled — frozen at load-frame world position.
- Invalid joint indices silently drop weight contribution (no renormalization).
- Multi-instance non-identity transforms in combined-buffer mode unsupported.
- Per-frame normal-matrix recomputation (dormant — normals not yet uploaded per frame).
- Hand-rolled joint-order remap (canonical USD path is `GetJointMapper()`).
- Rigidly-deformed mesh broadcast wastes ~236KB per hair-style mesh (planned `Rigid` enum variant).

**Lessons:**

- **Verify before fixing.** Six of 15 reviewer concerns were refuted by actually reading the code. Acting on every flag without verification would have introduced regressions.
- **Reviewers are best at flagging "this might be wrong" — they're not always right about what's wrong.** Both reviews disagreed with each other on several points, and the truth was usually a third thing only visible by reading the actual file at the actual line.
- **Lock-down tests prevent silent regression.** The non-identity geomBind test came directly from a reviewer concern that was wrong on the merits but right in spirit — the math IS easy to break in a refactor, and now there's a test that fails fast if someone does.

### Follow-up Commit 2: Rigid variant refactor (2026-04-11)

Landed the `SkinKind::{ PerVertex, Rigid }` enum on `SkinBinding`. Rationale: HumanFemale's hair mesh is 5899 verts × 5 influences, which the previous code broadcast into per-vertex layout as ~236KB of duplicate data when a single `(joint_idx, weight)` pair would suffice. Every rigid accessory mesh in a character does the same thing — multi-MB savings at load time.

**Changes:**
- **C++ bridge**: `cache_skeleton_data` now detects `IsRigidlyDeformed()` and SKIPS the post-split broadcast loop entirely — keeps `skin.joint_indices/joint_weights` as the single authored block. New `is_rigid` field on `CachedSkinBinding` + `UsdBridgeSkinBindingData` (uses `int32_t` for ABI stability).
- **Rust FFI**: `UsdBridgeSkinBindingDataRaw`, `UsdSkinBindingData`, `ffi_convert::convert_skin_binding`, and `UsdStage::get_skin_binding` all plumb the new flag.
- **`mesh::SkinBinding`**: refactored from flat struct (`joint_indices`/`joint_weights`/`element_size` at the top level) to `{ skeleton_path, kind: SkinKind, geom_bind_transform, inv_bind_matrices }`. `SkinKind::PerVertex` keeps the old flat fields; `SkinKind::Rigid { joint_idx, weight }` is the compact variant.
- **`skinning::skin_positions`**: matches on `kind`. Rigid path is a tight inner loop — one matrix lookup, one `transform_point3`, one `* weight` per vertex. No per-vertex array indexing.
- **`skinning::skin_normals`**: same match shape; rigid path skips the influence accumulation loop.
- **`loader.rs`**: branches on `skin_data.is_rigid` to construct the right variant. Logs whether the mesh was registered as rigid or per-vertex.
- **Test update**: `test_load_two_bone_arm_mesh_skin` in loader.rs now destructures `skin.kind` as `SkinKind::PerVertex { .. }`. Test fixture is per-vertex, so the variant is asserted explicitly.
- **New test**: `rigid_binding_round_trip` in `skinning.rs` with three sub-cases — identity joint, translated joint, out-of-range joint_idx (soft-fail). Total skinning unit tests: 10.

**What I deliberately skipped:**

The original review also suggested migrating the hand-rolled mesh→skel joint-order remap to `UsdSkelSkinningQuery::GetJointMapper()`. After researching the API, this turned out to be a deeper architectural choice, not a simple refactor: the mapper goes skel→mesh (for remapping joint *xforms* to per-mesh order), so adopting it canonically would mean flipping BIF's skinning architecture from "one global skel palette" to "one palette per mesh". The dedupe optimization in Commit 1 actually makes the global-palette approach more attractive (N FFI calls → 1 per skeleton), so the hand-rolled remap stays. Documented as a deliberate design choice in the wiki article rather than a TODO.

**Measurement:**

Didn't add an automated memory bench (HumanFemale exists but the unit tests don't load it). Eyeballed the diff: `skin.joint_indices` length for a hair mesh goes from `vert_count * element_size` to `1`. For the HumanFemale hair `Shell_sbdv` at 5899 verts × 5 influences that's 29495 entries → 1 entry, ~236KB → 4 bytes per array. Across accessories in a full character scene, multi-MB savings.
