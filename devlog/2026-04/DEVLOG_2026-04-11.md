The tracking doc just never got updated because each session focused on shipping the code, not maintaining the plan doc. Lesson: when closing a phase, update the plan doc in the **same commit** as the code, not in a separate "docs: update status" commit that gets deferred.
- The `StatsPanelParams` borrow-splitting pattern from `render_ui.rs` turned out to be unnecessary after sub-struct decomposition. Typed containers (`GpuContext`, `SceneManager`, etc.) let callers borrow orthogonal sub-fields independently, so most new code never needs the param-struct pattern. The old one stays as a one-off.

#### 8. Debugging hair/nails offset

- User reported hair/nails displaced on HumanFemale.walk.usd. Bisected: disabled C++ blend shape section (`#if 0`) + Rust loading (`bs_count = 0`). Hair/nails still offset with blend shape code completely disabled → **not a v0.13.6 regression**. Pre-existing issue (likely the documented v0.13.5 "per-instance non-identity transforms in combined-buffer mode" limitation). Logged for separate investigation.

### Key Decisions

1. **Dense expand in C++** — zero-pad sparse targets via pointIndices for auto-vectorizable Rust loop
2. **On-demand anim query** — resolve `UsdSkelAnimQuery` at eval time, not cache time (matches joint eval pattern, avoids cache side effects)
3. **Unclamped weights** — pass through per USD spec (>1.0 exaggeration, <0 anti-shapes legal)
4. **Hair/nails offset → separate bug** — bisection proved not caused by blend shape code

### Learnings

- USD `UsdSkelBlendShape` targets can be sparse (via `pointIndices`) or dense. Dense expansion in C++ simplifies the Rust hot loop at the cost of ~2-12MB/mesh memory.
- Shape-order remap needed: mesh's `skel:blendShapes` token order ≠ anim's `blendShapes` order. Built once at load in C++.
- Pipeline order matters: blend shapes must be applied BEFORE skinning (shapes deform bind pose, skinning transforms deformed positions).
- `thread_local` scratch buffers in C++ FFI functions work well for returning arrays of structs without lifetime management. The Rust side copies data in `convert_*` before the scratch is reused.

### What I Did

#### 2. Data collection (C++ debug logging)

#### 4. Cleanup

Removed debug logging, cleaned worktree, logged bug in BUGLIST.md.

### Key Decisions

1. **Bug is pre-existing** — not a v0.13.6 regression. Separate investigation needed.
2. **Logged to BUGLIST.md** — "Rigid-skinned mesh offset on animated characters"
3. **v0.13.6 blend shapes shipped clean** — no rollback needed

### Learnings

- Worktree A/B testing with separate `CARGO_TARGET_DIR` is the definitive way to confirm regressions on Windows (avoids CMake cache conflicts)

- USD rigid meshes in HumanFemale have vertices in skel-local space with identity geom_bind — the loading path is correct, issue is in per-frame skinning or GPU buffer write
