### Renderer decoupling (`crates/bif_viewport/src/lib.rs`, `render.rs`)

**New Renderer API:**

- `pub fn new(surface, device, queue, config, size: (u32, u32), scale_factor: f32) -> Result<Self>`
  — synchronous; caller owns wgpu primitive construction.
- `pub fn attach_egui(&mut self, egui_state: egui_winit::State)` — optional
  egui overlay attachment. `bif_viewer` calls this; `bif_qt` will not.
- `pub fn egui_state_mut() -> Option<&mut egui_winit::State>` — caller drives
  the winit ↔ egui handshake (`take_egui_input`, `on_window_event`,
  `handle_platform_output`) outside this crate.
- `pub fn egui_ctx() -> &egui::Context` — for reading `pixels_per_point`,
  pushing theme, etc.
- `pub fn set_dialog_focus_hook<F: Fn(bool) + 'static>(&mut self, hook: F)`
  — installable visibility toggle for the Windows z-order workaround; the
  existing 5 internal `with_dialog_focus` call sites route through this. No
  change to dispatch modules.
- `pub fn scale_factor() -> f32` + `resize((u32, u32), f32)` — scale stored
  on Renderer, updated on resize.
- Constants `REQUIRED_FEATURES` + `required_limits()` exposed so callers can
  request the right wgpu device.

**Removed:** `handle_egui_event` (caller drives `egui_state.on_window_event`
directly), old `resize((u32, u32))` signature, `window: Arc<winit::Window>`
field, `egui_winit::State` construction in `new()`.

**`render()` signature change:**

```rust
// before
pub fn render(&mut self, clear_color: wgpu::Color, window: &winit::Window) -> Result<()>
// after
pub fn render(
    &mut self,
    clear_color: wgpu::Color,
    raw_input: Option<egui::RawInput>,
) -> Result<Option<egui::PlatformOutput>>
```

`raw_input: None` = headless (3D only), `Some` = egui overlay. `submit_gpu_frame`
destructures `FullOutput` and returns `PlatformOutput` for the caller to hand
to winit. All egui passes inside `submit_gpu_frame` conditionalized on
`full_output.is_some()`.

**Zero direct `winit::*` imports** in `lib.rs` and `render.rs`. Remaining
references are doc comments and the `egui_winit::State` type (held as
`Option<egui_winit::State>` — winit transitive dep is unavoidable while egui
is still alive, and acceptable).

### bif_viewer compat shim (`crates/bif_viewer/src/main.rs`)

Added `fn create_renderer(window: Arc<Window>) -> Result<Renderer>` free
function that:

1. Builds `wgpu::Instance` + surface + adapter + device + queue + config (the
   setup that used to live inside `Renderer::new`).
2. Calls `Renderer::new(...)`.
3. Builds `egui_winit::State` from the winit window and calls `attach_egui`.
4. Installs `set_dialog_focus_hook(move |v| window.set_visible(v))`.

Replaced the 3 `pollster::block_on(Renderer::new(window.clone()))` sites with
`create_renderer(window.clone())` (sync — `pollster::block_on` moved inside
the helper for the adapter/device requests).

Replaced `renderer.handle_egui_event(window, &event)` with an inline
`egui_state_mut().on_window_event(window, &event).consumed` check.

Replaced `renderer.render(clear_color, window)` with a 3-step sequence:
`take_egui_input(window)` → `render(clear_color, Some(raw_input))` →
`handle_platform_output(window, platform_output)`.

Updated both `resize` call sites to pass `window.scale_factor() as f32`.

## Learnings

- **Handoff scope estimates can hide winit-through-egui coupling.** The
  "pull Renderer into bif_qt" plan assumed a simple type swap. Real
  coupling was 8 touchpoints across 2 files, 5 of which were structurally
  through `egui_winit::State`. Explore agent's pass-through read caught this
  before I burned time on a dead end.
- **`with_dialog_focus` pattern is a great fit for an installable hook.** 5
  internal callers would've had to bubble set_visible out to bif_viewer; one
  `Box<dyn Fn(bool)>` closure field keeps all of them unchanged while making
  Renderer windowing-system-agnostic.
- **egui's per-frame winit handshake is conceptually small**
  (`take_egui_input` pre-frame, `handle_platform_output` post-frame). Passing
  `Option<RawInput>` in and returning `Option<PlatformOutput>` lets
  `bif_viewport` stay egui-aware without being winit-aware.
- **Destructuring `FullOutput` lets us move `platform_output` upstream** while
  consuming the other fields in-place. Important because the new contract
  returns platform_output to the caller (can't call `handle_platform_output`
  here anymore — no winit Window).
- **Pulling wgpu primitive construction into the consumer is the right move
  long-term.** bif_viewer and bif_qt can each use their native window-system
  surface creation; `Renderer::new` is now a pure wgpu consumer and doesn't
  need winit-vs-Qt conditionals.

## Paused — Moves 2+4 architecture gate

Started Move 4 (USD timeline FFI) and realized `UsdStage::get_timeline()` + `UsdTimelineData { start_time_code, end_time_code, frames_per_second }` already exist in `bif_core/src/usd/cpp_bridge.rs:756`. No new FFI needed — Move 4 is just "wire the existing call into the invokable."

But that surfaced the real gate for Move 2: `BifShellState` invokables only see `Pin<&mut BifShellState>`; they have no path to `ViewportCallbacks::viewport.renderer.scene` where `SceneManager::load_usd_scene` lives. The two Rust singletons live in disjoint scopes (app.rs runtime vs cxx-qt QObject lifecycle).

Three realistic options (documented in SESSION_HANDOFF under "Next"):

- **α** — `Arc<Mutex<CommandQueue>>` shared between BifShellState + ViewportCallbacks. Invokables push commands, ViewportCallbacks drains at the top of each frame. ~50 LOC, clean. This is what the original handoff's AppEvent-bridge option (a) recommended.
- **β** — stash `*mut ViewportCallbacks` on BifShellState at startup. Invokables deref unsafely. Ugly but matches existing `app.rs` pattern.
- **γ** — make `Renderer.scene` an `Arc<Mutex<SceneManager>>`. Invasive — touches every `self.scene.*` site inside Renderer.

Paused here per the "foundation over visible progress" ethos — another architectural decision deserves a dedicated conversation, not a rushed pick.

## Move 2 + ADR-007 — thread-local raw-pointer bridge + real stage load

Fourth pass — locked in the architecture and shipped Move 2 in the same change.

**The flip on α → β.** Original handoff recommended α (`Arc<Mutex<CommandQueue>>`). Rethinking the real constraints exposed the α sales pitch was thread-safety-flavored — which doesn't apply. Qt UI is single-threaded, `SceneManager::load_usd_scene` is synchronous, there's no frame-coherence problem a queue would solve. β's "ugly" raw-pointer feel reduces to one small `unsafe` block when packaged through `thread_local!<Cell<*mut _>>` + a `with_viewport_mut(|vp| ...)` helper.

**ADR-007** (`wiki/architecture/adr/007-shell-state-to-viewport-bridge.md`) captures the decision: β chosen, α and γ (Arc<Mutex<SceneManager>> inside Renderer) rejected with rationale, safety invariant documented (single-threaded Qt UI + stack-owned ViewportCallbacks + install-before-event-loop).

**Implementation:**

- `crates/bif_qt/src/main_window.rs` — new module-level `thread_local!` + `unsafe fn install_viewport_callbacks(cb)` + `fn with_viewport_mut<R>(f) -> Option<R>` (3 lines of `unsafe` total).
- `crates/bif_qt/src/app.rs` — calls `install_viewport_callbacks(&mut viewport_cb as *mut _)` before `bif_qt_run_shell`. Pointer valid for event-loop lifetime.
- `on_stage_path_opened` invokable — now drives a real scene load:
  1. Records path (Move 4 behavior preserved).
  2. `with_viewport_mut(|vp| vp.renderer_mut().load_usd_scene(&path_buf))`.
  3. On `Some(Ok(()))` → clones `vp.renderer_mut().scene.layer_state` onto `BifShellState::scene_layer_state`, bumps `layer_state_revision` → Layer Stack panel refreshes with real data.
  4. On `Some(Err(_))` → status-bar error with the full `anyhow` chain.
  5. On `None` → viewport not ready (surface not yet created) — graceful no-op with a status-bar hint.

**`load_usd_scene` gotcha.** Explore agent earlier said the method lives on `SceneManager` at `scene_manager.rs:1481`. That line is actually inside an `impl Renderer` block in `scene_loader.rs` — the method is on `Renderer`, not `SceneManager`. Fixed the call site from `vp.renderer_mut().scene.load_usd_scene(...)` to `vp.renderer_mut().load_usd_scene(...)`. Caught on first `cargo build`.

## Dogfood bugs + follow-up fixes

User dogfooded `bif_qt_shell` and surfaced four issues. Addressed each:

**1. wgpu log spam.** `Device::maintain: waiting for submission index N` logged at INFO level every frame at 60 FPS. Env-logger filter now `info,wgpu_core=warn,wgpu_hal=error,naga=warn`. Also silences the Vulkan layer warnings from Galaxy Overlay / Rockstar Social Club JSON loader.

**2. `QFileDialog` didn't appear.** The native Windows file picker was stuck behind the main window — the 16ms wgpu paint tick kept the main window in the foreground. Tried first: `window->setVisible(false)/setVisible(true)` around `QFileDialog::getOpenFileName`. That worked but made the whole app briefly vanish — awful UX. Replaced with a surgical fix: `RenderWidget` now exposes `pausePainting` / `resumePainting` (the 16ms QTimer is now a member `m_tick` instead of a function-local static). `trigger_open_stage` pauses the tick around the picker so the native dialog stops fighting for z-order. Main window stays visible throughout.

**3. D3D12 `OBJECT_DELETED_WHILE_STILL_IN_USE` crash on close.** GPU resources dropped while commands in-flight. Added `Renderer::wait_for_gpu()` (calls `device.poll(Maintain::Wait)`) and invoked it from `viewport_on_shutdown` before `cb.viewport = None`.

**4. Second Renderer initialized + crash on File → Open.** Root cause: the `setVisible(false/true)` workaround re-triggered `showEvent` on the RenderWidget → `surfaceReady` signal → `viewport_on_surface_ready` unconditionally ran `Viewport::new` again, dropping the existing Renderer mid-frame. Guarded `viewport_on_surface_ready` — if `cb.viewport.is_some()`, just resize. Combined with fix #2 (removing `setVisible`) this would've been moot, but the guard is still correct defensive coding.

**5. Camera orbit / pan / zoom didn't navigate.** `on_camera_orbit/pan/zoom` were still Phase E.1 status-echo stubs. Wired through `with_viewport_mut` to `Renderer.cam.camera.orbit/pan/dolly` with `update_camera()` after each. Sensitivities: 0.005 for orbit (matches bif_viewer), distance-scaled for pan + zoom so navigation feels proportional at any zoom level.

## Shared Open Stage flow + first-launch fix

Second round of dogfood surfaced: launch-screen "Open USD" button loaded the viewport but no file dialog appeared. Root cause — `openStageClicked` was wired to `shell_state->on_open_stage()` (the Phase B status-echo stub), not the QFileDialog flow that the menu action used. Recent-stage clicks also just set a status message without loading.

**Fix:** extracted the Open Stage flow into a `trigger_open_stage()` static helper taking `(window, shell_state, central_stack, viewport, pre_picked_path)`. Menu → calls with empty pre_picked_path → shows picker. Launch-screen Open → same. Recent stages → calls with the pre_picked_path filled → skips picker. All three flows now route through one code path with the paint-tick pause built in. Shipped in `cc44a45`.

Also: `trigger_open_stage` swaps `central_stack->setCurrentIndex(1)` BEFORE calling `on_stage_path_opened`. Learned the hard way that `with_viewport_mut` returns `None` when the RenderWidget isn't visible — `surfaceReady` needs to have fired first.
