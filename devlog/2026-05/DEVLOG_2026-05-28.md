### Five distinct crash modes patched in cascade

1. **`convert_instancer_animation` — 24 GiB Vec OOM.** `time_sample_count * instance_count * sizeof(Mat4)` = `16000 * 33485 * 64 B` ≈ 24 GiB request → `alloc::handle_alloc_error` → fastfail.

   - ~10 count×stride sites in `ffi_convert.rs` switched to `safe_mul_count` (infallible converters drop the offending attribute on overflow).
   - Regression test `crates/bif_core/tests/rt_010_base_oom_regression.rs` (`#[ignore]`).

2. **`combine_with_transforms` — 16 GiB `Vec<Vertex>` OOM.** Pre-existing `Combined mesh too large for GPU` warn in `scene_loader.rs` runs AFTER the giant Vec was already built. Added pre-allocation guard at the top of `mesh_data.rs:601`: sum `total_verts × sizeof(Vertex)` + `total_indices × 4`, cap at 1 GiB, return empty MeshData → multi-draw fallback path takes over. Confirmed on rt_010: `Combined mesh skipped pre-build: 356237003 verts ~16307 MiB, 1952552475 indices ~7448 MiB — multi-draw only`.

3. **`Queue::submit` panics on device-lost.** wgpu 22's `Queue::submit` panics via `handle_error_fatal!` — **error scopes (`push_error_scope`/`pop_error_scope`) do NOT catch this**. The only reliable interception is `std::panic::catch_unwind`, which works because `panic = "unwind"` is the workspace default (no profile override).
   - Wrapped `MipmapGenerator::generate`'s submit (texture_loader.rs:175).
   - Wrapped `Renderer::submit_gpu_frame`'s submit + present (render.rs:916).
   - Wrapped `wait_for_gpu`'s `Device::poll(Wait)` (lib.rs:1232).
   - Wrapped the viewport `cb.viewport = None` drop in `viewport_on_shutdown` (`Device::drop` asserts `queue_empty()` which fails on a lost device).
   - Each catch logs once + calls `mark_gpu_unhealthy()`.

4. **Process-global `GPU_UNHEALTHY: AtomicBool`** in `bif_viewport::texture_loader`. `gpu_is_healthy()` / `mark_gpu_unhealthy()` accessors. Checked at:
   - `Renderer::render` entry (skip per-frame submit if dead).
   - `viewport_on_frame` (Qt cxx-qt bridge) — skip render entirely.
   - `poll_texture_loads` — drop receiver + early return.
   - `upload_streamed_texture` — early return.
   - `wait_for_gpu` — skip poll.

5. **`TextureBudget` on `GpuTextureSet`** (1.5 GiB default). `try_charge(width, height, mip_count)` predicts effective on-GPU size + mip chain (4/3 factor) before each `upload_raw_texture`. Logs one WARN on first overflow.

### Other wiring
- `device.on_uncaptured_error(...)` + `device.set_device_lost_callback(...)` installed in `bif_qt::Viewport::new` right after `request_device`. (Belt-and-suspenders — uncaptured handler doesn't catch `Queue::submit` panics, but does catch validation errors from other paths.)

## Key Decisions

- **`catch_unwind` over error scopes** — non-obvious but verified empirically: error scopes are documented to capture errors, but wgpu 22's fatal-path routes around them. Confirmed by reading `wgpu_core.rs:317` (`handle_error_fatal!`).
- **VRAM budget 1.5 GiB hardcoded** — works for ≥4 GiB discrete GPUs after Qt + swapchain + geometry. Per-machine dynamic budget (`DXGI QueryVideoMemoryInfo`) saved as separate plan at `C:\Users\brandon\.claude\plans\dynamic-vram-budget-from-system-capacity.md` for v0.17.
- **Mesh pre-allocation cap 1 GiB** — paired with GPU's `max_buffer_size` (typically 1 GiB on D3D12/Vulkan). Above this, multi-draw fallback is correct.
- **Process-global atomic for GPU health** — single device per process; per-scene reset isn't meaningful since a lost device is lost for the lifetime of the process. Atomic, no plumbing required.

## Learnings

- **wgpu error scopes only catch *non-fatal* validation errors.** `Queue::submit`, `Device::poll`, `Device::drop` all panic via `handle_error_fatal!` regardless of any active error scope. The `on_uncaptured_error` handler also doesn't intercept these. The ONLY way to survive them in user code is `std::panic::catch_unwind` (requires `panic = "unwind"`).
- **The 24 GiB number is a useful signature.** Two unrelated allocations both hit exactly `25_769_803_776` bytes (`6 × 2³² = 24 GiB`). For `Vec::push` growing a `Vec<Vertex>` (48 B each), 16 GiB consumed → next doubling requests 32 GiB? Actually no — the OOM signature comes from precomputed `Vec::with_capacity(total_count)` allocations where `total × elem_size == 24 GiB exactly`.
- **`STATUS_STACK_BUFFER_OVERRUN` (0xc0000409) is Windows `__fastfail(FAST_FAIL_FATAL_APP_EXIT)`** — it's what Rust's `panic = "abort"` fires AND what `alloc::handle_alloc_error` fires. Same exit code, very different recovery options.
- **cxx 1.0 prevents panic-over-FFI by aborting** — its `prevent_unwind` guard at the FFI boundary turns any unwinding panic that reaches it into a hard abort. So `catch_unwind` MUST live below the cxx-qt callback frame, not above it.
